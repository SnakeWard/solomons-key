# Trust Boundary

What this toolchain proves, what it assumes, and where the assumptions stop.

Written because an external review named the right gap: *"a rigorous research prototype and reference implementation, not yet a secure proof-of-computation system."* That is accurate. This document draws the line precisely, so nobody has to infer it.

---

## The root of trust

`TRUSTED_PROGRAMS.sha256`.

Every artifact declaring `evidence_source: program` names the binary that produced it and that binary's SHA-256. `sk-verify` RUN17 checks both against this allowlist.

The field meanings do not vary by producer:

- `produced_by_program.sha256` is always the producing executable's SHA-256.
- `input_sha256` is the digest of the file or value the program measured.
- `input_path`, when present, lets SEM06 recompute `input_sha256` from the file on disk.

RUN17 never substitutes an input digest for a missing executable digest. A program-produced artifact with no executable hash fails closed and explicitly warns against copying its input hash into the allowlist.

**That file is not verified by anything here.** It has to be pinned out of band — reviewed, signed, committed and diffed. Everything else in this toolchain reduces to trusting those hashes.

`sk_init.py` refuses to overwrite an existing trusted-programs file. Replacing one requires an explicit `--force`; creating a separate candidate requires `--trusted-out PATH`. On refusal or forced replacement it prints every active trust entry that would be lost.

This is the same shape as SLSA's trust in a build platform. The SLSA provenance spec says it plainly: the builder "is trusted to have faithfully recorded the provenance; there is no option but to trust the builder." Solomon's Forge moves the trusted component from a whole build platform to a small, hashed, single-purpose emitter — a narrower thing to review — but it does not eliminate it. Nothing can.

**What RUN17 does buy:** substitution becomes visible. A modified emitter records its own modified hash, and the allowlist rejects it. Verified by appending one comment line to `sk_emit.py` and re-emitting:

```
CRITICAL RUN17  [unbounded_actor_authority]
         gate_decision_artifact names 'sk_emit.gate' at 29d79602d2d6…,
         but the allowlist pins f868a1a8d99f… —
         the producing program was modified
```

**What it does not buy:** if `TRUSTED_PROGRAMS.sha256` is wrong, or the pinned emitter is itself flawed, the record is a lie with perfect provenance. Trust moved; it did not vanish.

## Ledgers: audit versus fixture

A hash-chained ledger proves nothing was rewritten within a lineage. It does not prove the lineage witnessed anything.

The genesis entry now carries `ledger_class`:

- **`audit`** — entries were appended as events occurred.
- **`fixture`** — the chain was seeded retroactively by a program reading a summary. It verifies. Nothing in it observed anything happen.

The shipped ledger is `fixture`, and says so structurally rather than in prose:

```
class fixture  (seeded demonstration — not an audit record)
```

RUN18 surfaces this on any run witnessed by a fixture chain. The reference run `runs/real` verifies at 0 critical, 0 error — and carries exactly one warning, that its witness is seeded. That warning is correct and should stay until a real audit ledger exists.

Two ledgers, one `audit` and one `fixture`, are the same data structure. Only the declaration distinguishes them, and the declaration is the operator's claim. **`ledger_class: audit` is an attestation, not a measurement.**

## Runs: real versus fixture

`runs/good` is generated by `gen_runs.py` with placeholder program hashes. It carries `"fixture": true`, and RUN00 states it must not be cited as evidence of a governed build.

RUN17 reports at WARN rather than CRITICAL on a declared fixture, since unrecognized program hashes are expected there. This is not an escape hatch: the price of the downgrade is the fixture flag itself, which disqualifies the run from ever being offered as proof.

`runs/real` is emitted by `sk_emit.py`. Twelve program-produced artifacts, one attestation (the role output, correctly labeled a claim), every hash matching the pinned emitter.

## What is proven

Given a trusted allowlist and an anchored ledger, `sk-verify` establishes that:

- every gate the route required has a recorded decision (**RUN06** — absence is the bypass);
- every automatic gate's decision was program-produced, transitively down its evidence chain (**RUN16** — a gate is only as automatic as its evidence);
- every producing program is one the allowlist recognizes, at the hash it recognizes (**RUN17**);
- validation ran, with no unjustified skips (**RUN12**);
- every artifact validates structurally and semantically, and its ledger reference resolves;
- the chain has not been rewritten within its lineage, and matches an external anchor.

---

## What is not proven

**Judgment.** Three gates are `attested`. An attestation is somebody's word — recorded, attributed, locatable, and not verified. This is marked in the manifest rather than obscured.

**Correctness of the trusted programs.** See above. `sk_emit.py` is 1,376 lines and has been reviewed by its author and one external reader.

**That a fixture ledger witnessed anything.** By construction it did not.

**Semantic correctness of the work.** A run can satisfy every gate and produce bad software. This verifies process evidence, not quality.

**Freshness.** Nothing binds a run record to wall-clock time beyond self-reported timestamps. There is no trusted timestamp authority. A run can be replayed.

**Non-collusion.** If the emitter, the ledger, and the allowlist are all under one actor's control, that actor can produce a self-consistent false record. Detecting that requires an independent witness — a transparency log with external monitors, in the manner of Certificate Transparency or Rekor. **This is the largest remaining gap and the natural next step.**

---

## Honest positioning

**This is a reference implementation of a verification model, not a secure proof-of-computation system.**

The distinction matters:

- A *proof-of-computation* system would make it infeasible for an adversary with local control to produce a false record — via hardware attestation, an independent transparency log, or reproducible re-execution by a third party.
- This makes a false record **structurally visible to anyone holding the allowlist and the anchor**, and makes the boundary between computed and asserted evidence explicit and machine-checkable.

That is a real property and a narrower one. Claiming the first when you have the second is the failure this project was built to detect, so the claim is stated at its true size.

---

## Closing the remaining gaps

1. **Independent witness.** Publish ledger heads to a transparency log with external monitors. Removes the single-actor collusion assumption — the largest gap.
2. **Reproducible re-execution.** Let a third party re-run the emitters against the same inputs and compare artifacts byte-for-byte. Determinism is already tested and enforced (SEM13), so the mechanism exists.
3. **Sign the allowlist.** Sigstore keyless signing over `TRUSTED_PROGRAMS.sha256` moves the root of trust from a file in the repo to an identity in a public log.
4. **Preserve raw evidence.** Artifacts currently record results and hashes, not the underlying output streams. Attaching raw captures would let a verifier re-derive a conclusion rather than accept a summary of it.
5. **Reduce the attested three.** Every gate promoted from `attested` to `automatic` shrinks the surface where somebody's word is load-bearing.
